# Isolated five-minute Android run

Use this procedure for every application in a **full** triage. The package name and complete APK/split set must already be established. This is a gated workflow: failure of image compatibility, VM isolation, boot verification, or fail-closed routing ends the dynamic phase before app installation. Report the gate and retain static findings. A VM is a containment boundary, not a proof of zero host interaction.

## 1. Select and identify Google's image

1. Read `minSdkVersion`, `targetSdkVersion`, and any `maxSdkVersion` from the **effective APK manifest** with `apkanalyzer`, `aapt2`, or an equivalent binary-manifest reader. Record all three values and whether a value was absent/defaulted. `targetSdkVersion` is a target **API level**, not a runtime image revision or the minimum installable version; [Android's `<uses-sdk>` reference](https://developer.android.com/guide/topics/manifest/uses-sdk-element) defines the distinction. Check APK native ABIs and features against candidate emulator images.
2. Refresh the stable Google SDK catalog inside the disposable analysis VM with the current [Android SDK manager](https://developer.android.com/tools/sdkmanager). List stable `system-images;android-<target-api>;...` packages and their revisions. Choose the newest **stable revision for that exact target API** that supports the needed ABI and app features. Record the variant (`google_apis`, `google_apis_playstore`, or another justified Google variant), ABI, package path, revision, catalog query time, and why it was selected. Do not substitute the latest Android OS release for an older target API without reporting a separate compatibility run. If no suitable exact-API image exists, stop and report that the specified dynamic environment is unavailable.
3. Download/install that package from Google's SDK repository through `sdkmanager`, and retain the install log and `source.properties`. Record any published archive checksum if available. Before first boot, SHA-256 hash `system.img` and every present companion boot image such as `vendor.img`, `ramdisk.img`, and `kernel-ranchu`; hash a sorted file-hash manifest to identify the complete system-image set. Preserve these hashes and the SDK/emulator/Platform Tools versions. Recheck the hashes after analysis if the image is expected to remain read-only. A locally computed hash identifies the tested bytes; it is not, alone, a publisher signature.

## 2. Boot without app egress or host reachability

- Run the Android Emulator and the later Docker gateway **inside a fresh disposable VM**, not on the analyst's host or in a host Docker container. Use an isolated virtual network rather than a bridged host LAN. Disable guest-visible host filesystem shares, clipboard/drag-and-drop, USB, audio/camera/microphone passthrough, host Docker socket, host ADB/TCP, and access to host loopback, gateway services, and metadata endpoints. Use a narrow, audited transfer mechanism only to import the APK set and export logs/evidence. Keep the VM OS, AVD data disk, and application data disposable; do not expose real accounts or personal data to the app.
- Prepare the VM and download the Google image and pinned gateway container image **before** starting Android. Apply default-deny Android egress in the VM's network policy before emulator startup; record the rules and counters. The guest's preparation traffic to Google or a container registry is separate from Android traffic. Do not give the Android guest unrestricted connectivity during its boot window.
- Create a fresh AVD with the selected system-image package. Start the emulator with a clean userdata image and no saved snapshot (for example, `-wipe-data -no-snapshot -no-window -no-audio` where supported; check the installed emulator's help). Google's [emulator command-line guide](https://developer.android.com/studio/run/emulator-commandline) documents these switches and the image files. Keep ADB bound within the analysis VM. Capture the boot log, AVD configuration, emulator version, VM ID/base-image hash, network rules, and boot start time.
- Wait for the intended emulator serial, `adb wait-for-device`, `getprop sys.boot_completed` equal to `1`, and package-manager responsiveness. Record `ro.build.version.sdk`, `ro.build.version.release`, `ro.build.fingerprint`, and `ro.product.cpu.abi`; compare them with the selected package and manifest constraints. Verify attempts from Android to reach host-only/private addresses and direct internet are denied before continuing. A booted ADB transport alone is insufficient.

## 3. Start and verify the Tor/Privoxy gateway

- **After Android boot is verified**, start Tor and Privoxy in a Docker container inside the disposable VM. Use a reviewed image/Dockerfile pinned by digest; record its digest, Dockerfile/config hashes, Tor/Privoxy versions, and launch command. Keep it on a private guest network, without `--network=host`, `--privileged`, host mounts, or Docker-socket access. Apply least privilege and resource limits where supported. Privoxy can forward all HTTP(S) requests to Tor's SOCKS port using `forward-socks5t / 127.0.0.1:9050 .` when both processes share the container namespace; see the [Privoxy forwarding manual](https://www.privoxy.org/user-manual/config.html). Do not add private-network bypass rules.
- Enforce a VM-network **fail-closed** rule set: Android may reach only the gateway's private listener; only the gateway may make Tor bootstrap/relay connections. Redirect or block direct DNS, direct TCP, UDP/QUIC, IPv6, local/LAN, and host-bound attempts. Tor SOCKS carries TCP and does not support SOCKS5 UDP association, per the [Tor specification](https://spec.torproject.org/socks-extensions.html); unsupported traffic must fail rather than escape. An emulator `-http-proxy` or Android `http_proxy` setting can help proxy-aware flows, but it does not prove that every app socket is routed. Save the actual firewall/routing configuration and counters.
- Require evidence from **inside Android** of a successful request through the gateway and Tor, plus negative tests showing direct TCP, DNS, UDP, IPv6, and host/private-address attempts are blocked. Record the probe method, endpoint, timestamps, gateway/Privoxy/Tor logs, and VM egress capture or counters. Verify that stopping the gateway makes Android outbound traffic fail closed, then restart and reverify it. If any test fails or cannot be observed, leave the APK uninstalled and mark dynamic analysis blocked. A Tor exit-IP check alone cannot establish absence of leaks.

## 4. Capture baseline, install, launch, observe for 300 seconds

Immediately before installation, capture a read-only baseline of every accessible writable Android partition and hash each raw snapshot. Follow the [filesystem and VirusTotal procedure](filesystem-and-virustotal.md) for snapshot scope, extraction, comparison, and lookup rules. Do not treat a partial ADB inventory as complete.

1. Import only the already-identified APK/split set through the controlled transfer channel. Rehash it inside the VM and compare with intake hashes. Save boot logs, then begin a separate timestamped install/run logcat capture (`adb -s <serial> logcat -b all -v epoch`, or an equivalent supported format). Use `adb -s <serial> install` for a single APK or `install-multiple` for a complete split set. Save exit status and `dumpsys package`/`pm path` evidence that the requested package and expected version were installed. Do not install mismatched splits or a different package.
2. Launch the manifest launcher component (or documented intended entry point) using `am start`. Record the exact component/action, launch result, foreground activity and process/PID evidence, and a monotonic launch timestamp. Start the five-minute clock only after a confirmed launch; observe for **300 seconds** without introducing real credentials or uncontrolled user data. Record any deliberate interactions. If the app exits, crashes, or never reaches a running state, record the actual duration and outcome; do not label it a completed five-minute run.
3. After observation and before discarding the AVD, capture a matching final writable-file snapshot. List and hash every created, modified, or deleted regular file in the captured scope; preserve before hashes for deleted and modified files. Query existing VirusTotal reports for the APK/split SHA-256 values and every distinct created-file SHA-256, without uploading content. Record missing, authentication-unavailable, and rate-limited lookups. Export full logcat for install and run, Android crash/ANR/tombstone evidence where available, package/permission state, Tor and Privoxy container logs, gateway health, network-denial counters, and a bounded packet capture or connection summary. Hash every exported file, including raw snapshots and the complete file-change inventory, and record UTC start/end timestamps, monotonic duration, tool versions, image/container digests, and any missing evidence. A proxy log shows a request that reached the proxy; it does not establish that all app traffic did. Preserve raw logs privately and redact secrets, tokens, identifiers, and sensitive URLs in any public handoff.
4. Shut down the emulator and gateway, export the evidence through the narrow channel, and discard the VM/AVD writable state. Report teardown status. Do not reuse a potentially contaminated snapshot for a different app.

## Handoff fields

Include a compact dynamic-run table with: requested/observed package and APK/split hashes; manifest min/target/max API; selected Google image package, variant, ABI, revision, catalog time, and SHA-256 of each image file plus set manifest; booted Android release/API/build fingerprint; emulator/VM identity and isolation checks; Docker gateway digest and Tor/Privoxy versions; firewall/proxy positive and negative test results; install/launch result; exact observed duration; UTC start/end; crash/ANR findings; snapshot scope and hashes; complete file-change inventory link, count, and hash; VirusTotal lookup results and gaps; log/evidence paths and hashes; and any blocked or unverified gate. Link representative log excerpts to the full evidence. Keep static URL literals separate from runtime-observed destinations, and label traffic or file changes that may be emulator or SDK baseline rather than app-initiated.
